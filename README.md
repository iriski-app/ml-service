# ИрискИ: Python ML-сервис для бэкенда

Сервис предоставляет **gRPC**, а не пользовательский HTTP API. Go бэкенд владеет сессиями, PostgreSQL, исходным расчётом DV01, стресс-формулой и итоговыми суммами. Он передаёт этому сервису признаки для моделей либо факты готового расчёта для текстового объяснения.

## Текущее состояние

- Типизированный контракт `proto/ml_service/v1/service.proto` и сгенерированные Python файлы сервера готовы. Go клиент генерирует команда бэкенда из того же контракта в своём репозитории.
- Сервис умеет загружать CatBoost артефакты, проверять их контрольные суммы и выполнять вывод моделей. **Рабочих артефактов моделей в репозитории нет.** Отсутствующие модели честно отмечаются в `GetReadiness`; соответствующий метод возвращает `FAILED_PRECONDITION`.
- LLM метод и проверка ответа реализованы. Основной вариант — вызов сохранённой конфигурации Yandex AI Studio через Responses API: модель и инструкция редактируются в AI Studio. Прямой вызов модели доступен только как явно выбранный отдельный режим. Ключ в репозитории не хранится.
- Тесты создают маленькие временные модели, чтобы проверить механику загрузки и gRPC. Они не подтверждают качество реальных моделей.

## Три метода сервиса

| Метод | Когда вызывает Go бэкенд | Что возвращает Python сервис |
| --- | --- | --- |
| `EstimateMissingMetric` | До DV01, если не хватает дюрации или выпуклости | Значение, источник, версию модели, при наличии интервал и отметку `review_required` |
| `AnalyzeScenario` | По запросу анализа готового стресс-сценария | Вывод одобренной сценарной модели по позициям, с явными `target_kind` и `target_unit` |
| `ExplainCalculation` | Только когда пользователь запросил объяснение готового расчёта | Проверенный текст, `calculation_id`, ссылки на `fact_ids` и версию LLM |

В `proto` также есть `GetReadiness`: он показывает готовность каждой возможности отдельно. Стандартный gRPC health endpoint показывает, что процесс жив. Отсутствие модели не препятствует запуску процесса, но не выдаётся за готовый ML прогноз.

### Восстановление метрик

Ноутбук `notebooks/price_imputation/03_catboost.ipynb` обучает отдельные CatBoost модели для `duration_mod` и `convexity`, а также модели интервалов. Сервис повторяет его порядок признаков и обратное преобразование `expm1`. Он **сохраняет наблюдаемое значение без замены**, если Go его передал. Для оценки пропуска нужны признаки облигации на дату расчёта; поддерживаются обычные фиксированные и бескупонные, неструктурированные облигации с точным календарём и валютой/сроком в области обучения. Оценка помечается как требующая проверки. Если важные признаки отсутствуют или бумага вне области применения, сервис отвечает ошибкой.

Известное ограничение исследования: интервалы на поздних датах не достигли номинального покрытия 80%. Это не гарантия точности для любого реального пропуска.

### Анализ сценария

Ноутбук `notebooks/rate_sensitivity/02_linear_regression_catboost.ipynb` обучает CatBoost на **синтетической цели**, полученной из формулы дюрации и выпуклости для условной позиции в десять номиналов. Это не наблюдаемое изменение рыночной цены и не прогноз для произвольной корзины. В ноутбуке тест использован для ранней остановки; перед продуктовым применением нужны отдельная валидация, независимый тест и согласование цели модели с бэкендом.

Скрипт упаковки такой модели ставит `approved_for_service=false`. Поэтому сценарный метод недоступен, пока команда не утвердит цель, единицы, проверенный диапазон и артефакт. Бэкенд при этом выполняет свой детерминированный стресс-расчёт без ML. Python сервис не меняет его суммы.

### Объяснение LLM

Бэкенд передаёт только факты готового расчёта: ID, тип (`DV01` или `STRESS_CHANGE`), дату, валюту RUB, итог и вклады позиций. Денежные значения в `ExplainCalculationRequest` передаются десятичными строками. Сумма `positions[].value_rub` должна совпадать с `total_rub`; `change_rub` передаётся отдельно для стресс-сценария. Этот смысл полей нужно подтвердить с бэкендом: стоимость позиции и её изменение нельзя смешивать. Для DV01 значения — вклады в риск, а не рыночная стоимость корзины.

Для объяснения **как посчитали** добавлены необязательные поля: `method=EXPLANATION_METHOD_DURATION_CONVEXITY`, `yield_shift_bp`, а у каждой позиции — `isin` и `inputs`. В `inputs` передаются фактически использованные `current_fair_value` (абсолютная неотрицательная стоимость позиции в её валюте), `position_currency`, `fx_rate_to_rub`, `duration_mod`, `convexity`, `duration_source`, `convexity_source`, `coupon_type` и при необходимости `coupon_frequency`. При подробном объяснении `value_rub` означает вклад в выбранную риск-метрику; для стресса `change_rub` должен совпадать с ним. Направление применяется один раз: покупка — положительный знак, продажа — отрицательный. Данные и FX берутся из исходного снимка, а не из текущих котировок.

До вызова LLM Python проверяет согласованность результата с переданными параметрами по формуле с допуском в одну копейку. Это проверка входов, не пересчёт результата для показа пользователю. DV01 требует сдвиг `+1 bp`; для стресса используется переданный параллельный сдвиг доходности. Ставка ЦБ и доходность облигации не отождествляются. Перевод bp в долю и процентные пункты добавляется как проверяемый факт. Для плавающего купона проверяется правило из общего ТЗ: дюрация равна обратной частоте выплат, выпуклость равна нулю, источник обеих метрик — `METRIC_SOURCE_COUPON_RULE`. Для обычных бумаг источник — `OBSERVED` или `CATBOOST`. CatBoost автоматически отмечает оценочный характер метрики.

Ответ дополнен `calculation_details_available` и `limitations`. Старые запросы без новых полей продолжают работать: возвращается `false` и ограничение, что исходные параметры не переданы. Полный разбор подстановки в формулу для них не заявляется. Существующие номера полей и RPC сохранены; бэкендеру нужно передать обновлённый `.proto`, перегенерировать свой клиент и начать заполнять новые поля. Python не может восстановить эти входы из одного ISIN или итоговой суммы.

Изменения общего `proto/ml_service/v1/service.proto` для команды бэкенда:

| Сообщение / enum | Добавлено | Что передавать / читать |
| --- | --- | --- |
| `MetricSource` | `METRIC_SOURCE_COUPON_RULE = 3` | Источник метрик, полученных по правилу плавающего купона |
| Новый `ExplanationMethod` | `EXPLANATION_METHOD_DURATION_CONVEXITY = 1` | Выбрать для подробного объяснения метода дюрации и выпуклости |
| `ExplanationPosition` | `isin = 6`, `inputs = 7` | ISIN и фактические входы исходного расчёта |
| Новый `PositionCalculationInputs` | `current_fair_value`, `position_currency`, `fx_rate_to_rub`, `duration_mod`, `convexity`, `duration_source`, `convexity_source`, `coupon_type`, `coupon_frequency` | Абсолютная стоимость позиции в исходной валюте, исходный курс и метрики с их источниками; частота выплат обязательна для плавающего купона |
| `ExplainCalculationRequest` | `yield_shift_bp = 10`, `method = 11` | Сдвиг в bp (`+1` для DV01) и выбранный метод |
| `ExplainCalculationResponse` | `calculation_details_available = 7`, `limitations = 8` | Доступен ли подробный разбор и какие ограничения нужно показать |

Для подключения Go клиенту нужен адрес Python gRPC сервиса (порт по умолчанию `50051`), обновлённый контракт и дедлайн, например 25 секунд при бюджете LLM 20 секунд. API-ключ Яндекса хранится только в окружении Python сервиса; в gRPC запросе и браузере он не нужен. `ExplainCalculation` вызывается отдельно по запросу пользователя и не участвует в вычислении DV01. При ошибке объяснения готовый финансовый расчёт должен оставаться доступным.

Сервис получает краткий русский текст через настроенный HTTPS провайдер и проверяет существование ссылок и числовые токены по явно указанным фактам. Проверка учитывает десятичную запятую, знак минуса, экспоненты, пробелы в числах и числа вплотную к единицам; числовой ID не разрешает использовать его как финансовый факт. Неподтверждённый текст не возвращается. `verified=true` означает прохождение этих проверок, а не доказанную правильность смысла всего текста: соответствие числа нужной позиции, единицам, выводам и числительные словами требуют отдельной проверки качества. До подключения к интерфейсу согласуйте эту трактовку с задачей 3_6.

## Получение артефактов моделей

Артефакты загружаются **один раз при старте** из `MODEL_DIR`; в этот каталог не кладут исходные данные пользователя. После добавления новых файлов процесс надо перезапустить.

### Модель пропусков

В текущем Git нет обученных `.cbm` и датасета `model_dataset.parquet`. Получите согласованную версию датасета у автора модели, выполните `notebooks/price_imputation/03_catboost.ipynb` и получите `duration_mod.cbm`, `convexity.cbm`, две модели интервалов и `metadata.json`. Затем создайте deployment manifest с областью обучения и контрольными суммами:

```sh
python scripts/prepare_imputation_bundle.py \
  --models-dir notebooks/price_imputation/data/models \
  --dataset notebooks/price_imputation/data/model_dataset.parquet \
  --splits notebooks/price_imputation/data/metric_model_splits.parquet \
  --output-dir models/imputation \
  --version imputation-v1
```

Для `read_parquet` скрипту нужен `pyarrow` (`python -m pip install pyarrow`). Каталог `models/imputation` должен содержать все файлы и `deployment.json`. Скрипт не обучает модель и не подтверждает её качество; версию и допустимость применения утверждают автор модели и команда.

### Сценарная модель

Сейчас ноутбук не экспортирует обученную модель. После **отдельного согласования цели и проверки на независимых данных** модель можно сохранить из ноутбука вызовом `cb_model.save_model("scenario.cbm")` и упаковать:

```sh
python scripts/prepare_scenario_bundle.py \
  --model-file scenario.cbm \
  --output-dir models/scenario \
  --version scenario-prototype-v1
```

Скрипт намеренно создаёт `approved_for_service=false`. Перевести модель в рабочее состояние можно только после согласования `target_kind`, `target_unit`, единиц признаков, допустимого диапазона и проверки качества; при смене цели потребуется обновить адаптер и контракт. Нельзя просто переименовать синтетическую цель в рыночный прогноз.

## Запуск

Нужен Python 3.12+. Для разработки:

```sh
python -m pip install -r ml_service/requirements.txt
MODEL_DIR=./models ML_GRPC_LISTEN=127.0.0.1:50051 python -m ml_service.server
```

В PowerShell переменные задаются через `$env:MODEL_DIR = '...'; $env:ML_GRPC_LISTEN = '127.0.0.1:50051'` перед командой `python -m ml_service.server`.

### Yandex AI Studio: инструкция в сохранённой конфигурации

1. В Yandex AI Studio получите ID каталога и API-ключ сервисного аккаунта с ролью `ai.languageModels.user` и областью `yc.ai.foundationModels.execute`.
2. Скопируйте `.env.example` в локальный `.env` и заполните пустые `YANDEX_FOLDER_ID` и `YANDEX_API_KEY`. `.env` и его локальные варианты исключены из Git. Ключ не передавайте в чат или в аргументы команд.
3. Откройте **Agent Core → Responses API → Конфигурации → Создать конфигурацию**. Форма может называться «Новый агент», справа указано «Тестирование конфигурации». Выберите модель DeepSeek, выключите рассуждение, установите температуру 0 и максимум 2000 выходных токенов. Для существующей конфигурации «ИрискИ» достаточно заменить инструкцию ниже и сохранить её. Навыки, поиск, MCP, инструменты и переменные для этой задачи не нужны.
4. Вставьте инструкцию ниже и сохраните конфигурацию. Скопируйте её ID в `YANDEX_PROMPT_ID`. В шаблоне уже выбран `LLM_PROVIDER=yandex_configuration`. Не используйте здесь ID нового агента Agent Atelier из URL `/runtime-agents/...`: это другой ресурс. Для фиксированной версии можно задать `YANDEX_PROMPT_VERSION`; пустое значение использует версию конфигурации по умолчанию.
5. Передайте переменные процессу через менеджер секретов, настройки запуска IDE или загрузите свой `.env` в shell:

```sh
set -a
. ./.env
set +a
MODEL_DIR=./models ML_GRPC_LISTEN=127.0.0.1:50051 python -m ml_service.server
```

```

Сам Python сервис `.env` автоматически не загружает. SDK для Yandex не нужен: используется стандартный HTTPS клиент. Endpoint — `https://ai.api.cloud.yandex.net/v1/responses`, авторизация — `Authorization: Api-Key ...` и `OpenAI-Project`. В запросе передаются `prompt.id`, при необходимости `prompt.version`, и факты в `input`. Python не подменяет модель, инструкцию, режим рассуждения и лимит токенов выбранной конфигурации. Ответ запрашивается через JSON Schema (`text`, `fact_ids`), затем проходит локальную проверку; само наличие JSON не делает ответ проверенным.

Каждое объяснение — отдельный запрос без истории другого расчёта: `store=false`, без `conversation` и `previous_response_id`. Внешние инструменты отключены в запросе (`tools=[]`, `tool_choice=none`), потому что объяснение должно использовать только факты бэкенда. Отказ, незавершённый ответ или неожиданный вызов инструмента не возвращается как проверенный текст.

`LLM_TIMEOUT_SECONDS` для сохранённых конфигураций по умолчанию 20 секунд: бюджет вызова с повторами; каждая HTTP попытка получает оставшееся время, ограниченное дедлайном gRPC. Сетевой таймаут применяется к блокирующим операциям транспорта. `LLM_RETRIES` по умолчанию 1 (максимум 2 повтора). Повторяются сетевые сбои, HTTP 429 и 5xx; ошибки авторизации, другие 4xx, редиректы, обрезанный ответ и неправильный JSON не повторяются. Финансовые данные и ключ в логи не попадают; редиректы с ключом не выполняются. Текст DV01-расчёта без названия метрики отклоняется. Эта проверка не доказывает правильность всех формулировок.

Если провайдер не настроен, объяснение возвращает `FAILED_PRECONDITION`; ошибка сети или провайдера — `UNAVAILABLE`, исчерпание дедлайна — `DEADLINE_EXCEEDED`, неверный ответ или неподтверждённые числа/ссылки — `DATA_LOSS`. Непроверенный текст не отдаётся, автоматической запасной сводки нет. `explanation_ready` проверяет наличие конфигурации, а не доступность внешнего API или действительность ключа.

При отсутствии `YANDEX_PROMPT_ID` выбранный режим возвращает `FAILED_PRECONDITION`; автоматического перехода на прямой вызов модели нет.

### Другие явно выбираемые провайдеры

- `LLM_PROVIDER=yandex`: прямой вызов модели через chat completions, `YANDEX_FOLDER_ID`, `YANDEX_API_KEY`, `YANDEX_MODEL=deepseek-v4.1-flash`. Инструкция в этом режиме находится в Python. `LLM_REASONING_EFFORT=none` отключает рассуждение, если модель поддерживает параметр. Его значение не используется в режиме сохранённой конфигурации. Лимит HTTP по умолчанию для прямого режима — 8 секунд; можно явно увеличить `LLM_TIMEOUT_SECONDS`.
- `LLM_PROVIDER=openai_compatible` (также значение по умолчанию при отсутствии переменной): `LLM_API_URL`, `LLM_MODEL`, `LLM_API_KEY`; используется Bearer-авторизация.

Официальные источники: [сохранённые конфигурации и отличие от новых агентов](https://aistudio.yandex.ru/ru/docs/ai-studio/operations/agents/migrate-prompt-id), [Responses API](https://aistudio.yandex.ru/ru/docs/ai-studio/api/Responses/createResponse), [модели и URI](https://aistudio.yandex.ru/ru/docs/ai-studio/concepts/generation/models), [аутентификация](https://aistudio.yandex.ru/en/docs/ai-studio/api-ref/authentication).

docker run --rm --env-file .env -p 127.0.0.1:50051:50051 iriski-ml
```

При наличии подготовленных CatBoost артефактов добавьте `--mount type=bind,src=/абсолютный/путь/models,dst=/models,readonly` перед именем образа. Без артефактов процесс запускается и может объяснять переданный готовый расчёт через LLM; `metric_ready` и `scenario_ready` будут `false`. В образ копируется только код сервиса и его зависимости, секреты и ноутбуки не включаются. Процесс работает от непривилегированного пользователя. Внешнее gRPC соединение требует доверенной сети или TLS на инфраструктурном прокси.

### Пробный запрос объяснения

После запуска сервиса выполните из корня репозитория в другом терминале с тем же Python окружением. Это **реальный платный запрос** к настроенному провайдеру, с вымышленными тестовыми фактами:

```sh
python - <<'PY'
import grpc
from ml_service.v1 import service_pb2 as pb, service_pb2_grpc as rpc

with grpc.insecure_channel("127.0.0.1:50051") as channel:
    answer = rpc.MLServiceStub(channel).ExplainCalculation(
        pb.ExplainCalculationRequest(
            request_id="smoke-1", calculation_id="demo-calc-1",
            calculation_kind=pb.CALCULATION_KIND_DV01, currency="RUB",
            total_rub="-199.97", data_as_of="2026-11-17",
            yield_shift_bp=1, method=pb.EXPLANATION_METHOD_DURATION_CONVEXITY,
            positions=[pb.ExplanationPosition(
                position_id="demo-position-1", isin="RU000A0JX0J2", side="buy", value_rub="-199.97",
                inputs=pb.PositionCalculationInputs(
                    current_fair_value="1000000", position_currency="RUB", fx_rate_to_rub="1",
                    duration_mod=2, convexity=6, coupon_type="fixed",
                    duration_source=pb.METRIC_SOURCE_CATBOOST,
                    convexity_source=pb.METRIC_SOURCE_OBSERVED,
                ),
            )],
        ), timeout=25,
    )
    assert answer.verified and answer.calculation_id == "demo-calc-1"
    assert answer.calculation_details_available
    print(answer.text)
    print(list(answer.fact_ids), answer.model_version)
PY
```

## Как связать с Go бэкендом

1. Передайте бэкенд разработчику `proto/ml_service/v1/service.proto`. Он генерирует Go клиент **в репозитории backend** через `protoc-gen-go` и `protoc-gen-go-grpc`; `go_package` в контракте указывает на `github.com/iriski-app/backend/internal/clients/ml/v1`. Изменения полей оформляйте новой согласованной версией контракта.
2. Go бэкенд создаёт gRPC клиент с адресом `ML_GRPC_ADDRESS`, ставит дедлайн на каждый запрос и передаёт `request_id`. Сессии и проверка доступа остаются **только в бэкенде**.
3. При отсутствии дюрации или выпуклости Go вызывает `EstimateMissingMetric` и передаёт признаки облигации на ту же дату, что и исходные данные. `observed_value` передают лишь когда хотят получить его неизменённым. При ошибке Go не подставляет придуманное число. В существующем backend в `internal/service/calculation.go` уже есть `TODO: Отправка в ML` при отсутствии дюрации.
4. После детерминированного стресс-расчёта Go **по желанию** вызывает `AnalyzeScenario`; не заменяет его результатом собственные суммы. Пока сценарная модель не одобрена, ожидает `FAILED_PRECONDITION` и показывает расчёт без ML анализа.
5. Для объяснения Go по запросу пользователя вызывает `ExplainCalculation` с фактами уже сохранённого расчёта. Для разбора **как посчитали** он передаёт новые `method`, `yield_shift_bp` и `positions[].inputs`, включая фактические источники метрик. Он показывает текст только при `verified=true` и совпадении `calculation_id`; при `calculation_details_available=false` учитывает ограничение об отсутствии параметров. LLM не вызывается при расчёте DV01.

Ошибки gRPC используют обычный статус (`INVALID_ARGUMENT`, `FAILED_PRECONDITION`, `OUT_OF_RANGE`, `UNAVAILABLE`, `DATA_LOSS`) и `google.rpc.ErrorInfo` с `request_id` и именем метода. Сервис ограничивает сообщение 1 MiB и сценарий 1000 позициями. Логи содержат метод, ID запроса, статус и время; финансовые значения и ключ провайдера не логируются.

## Проверка и генерация контракта

```sh
python -m unittest discover -s ml_service -t . -p 'test_*.py'
```

Тесты Yandex используют мок HTTP провайдера и настоящий локальный gRPC сервер: проверяют авторизацию, URI модели, JSON Schema, ответы, ошибки, дедлайны, повторы, неверные числа/ссылки, отсутствие провайдера и отсутствие секретов в журнале. Ключ не нужен, внешних платных вызовов в тестах нет.

Для проверки стиля установите `ml_service/requirements-dev.txt` и выполните `ruff check ml_service scripts`.

Для повторной генерации Python файлов установите `ml_service/requirements-dev.txt` и запустите `sh scripts/generate_grpc.sh`. Go клиент бэкенд генерирует из **того же `.proto`**. Тесты создают временные маленькие CatBoost модели и не требуют продуктовых артефактов.

Аналитические ноутбуки и их зависимости остаются в `notebooks/` и корневом `requirements.txt`; обучение и обслуживание gRPC сервиса разделены.
